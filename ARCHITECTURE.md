# Архитектура

## Процессы

```
┌────────────── main (Node.js) ──────────────┐      ┌──────── renderer (Chromium, sandbox) ────────┐
│ index.ts          жизненный цикл            │      │ app/App.tsx        корень                    │
│ windows/          окно, геометрия окна      │      │ layouts/           каркас окна               │
│ security/         протокол app://, CSP,     │ IPC  │ components/ panels/ toolbar/ dialogs/        │
│                   запреты навигации         │◄────►│ stores/            Zustand                   │
│ ipc/              обработчики + валидация   │      │ services/commands  реестр команд             │
│ services/         настройки, атомарная запись│     │ features/          функциональные модули     │
│ menu/             нативное меню (macOS)     │      │ engine/            PDF-движок (с фазы 2)     │
└─────────────────────────────────────────────┘      └──────────────────────────────────────────────┘
                         ▲                                              ▲
                         └────────── preload/index.ts ──────────────────┘
                              contextBridge: window.api (4 раздела, фиксированные каналы)

shared/  — типы, zod-схемы, каналы IPC, модель меню и команд, переводы. Используется всеми процессами.
```

## Безопасность

- `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `webviewTag: false`.
- Renderer загружается с `app://bundle/…`. Обработчик протокола отдаёт только файлы из каталога
  сборки (`resolveBundlePath` отклоняет `..`, закодированные обходы, нулевые байты).
- CSP в продакшене: `default-src 'none'; script-src 'self'; style-src 'self'; …` — без `unsafe-inline`.
  В dev-режиме политика ослаблена ровно настолько, насколько нужно Vite HMR.
- Любая навигация за пределы приложения, `window.open`, `<webview>` и запросы разрешений блокируются.
- Preload не даёт общего `invoke/send`: каждый метод привязан к одному каналу.
- Каждый обработчик IPC проверяет отправителя (верхний фрейм нашего origin) и валидирует данные zod-схемой.

## Команды и меню

`shared/menu/commands.ts` — каталог всех команд (идентификатор, фаза, ускоритель, роль).
`shared/menu/menuModel.ts` — дерево меню, единое для нативного меню macOS и меню внутри окна.

Команда активна в интерфейсе, только если у неё есть реальный обработчик в
`renderer/services/commands.ts` (или нативная роль). Иначе пункт меню и кнопка неактивны и
показывают, на какую фазу запланирована функция. Так интерфейс не может «притворяться».

Поток на macOS: renderer публикует состояние команд → main перестраивает нативное меню →
клик по пункту отправляет идентификатор в renderer → выполняется обработчик.

## Настройки

`main/services/settingsStore.ts` — единственный владелец настроек. Renderer применяет изменение
оптимистично и отправляет патч; main валидирует, сливает, пишет атомарно (temp → fsync → rename)
и рассылает итог. Повреждённый файл не удаляется, а переименовывается в `settings.json.corrupt-*`.

## Локализация

Переводы — `src/shared/locales/{en,ru,uk}/translation.json`. Renderer использует i18next,
main — лёгкую функцию `translate` для нативного меню. Тест проверяет совпадение ключей и
плейсхолдеров во всех языках и наличие подписи у каждой команды.

## Просмотр PDF (реализовано в фазе 2)

```
main: readPdfFile ──IPC──► documentActions ──► loadPdf (PDF.js, воркер) ──► PdfSource
                                   │                                          │
                                   ▼                                          ▼
                         documentsStore (модель)                  pageRenderer (реестр + кеш)
                                   │                                          ▲
                                   ▼                                          │
                  PdfViewer / ThumbnailsPanel ──► layout, zoom ──► PageView ──┘
```

- `engine/pdf` — интерфейс `PdfSource` и его реализация на PDF.js. Остальной код зависит только от
  интерфейса, поэтому в юнит-тестах движок подменяется.
- `engine/rendering/layout.ts`, `zoom.ts` — чистые функции раскладки, видимых страниц и масштаба.
  Виртуализация не измеряет DOM.
- `engine/rendering/pageRenderer.ts` — реестр источников вне React-состояния и LRU-кеш растров
  с бюджетом по пикселям.
- `engine/coordinates/pageCoordinates.ts` — единственное место преобразований PDF ↔ вид ↔ устройство.
- `stores/documentsStore.ts` — документы и их состояние просмотра; у каждого документа своё.
- Объекты PDF.js никогда не попадают в стор: их жизненным циклом управляют `registerSource` / `releaseSource`.

## Управление страницами и сохранение (реализовано в фазе 3)

- **Модель:** `PageModel = { id, source, box, rotation }`, где `source` — страница исходного PDF,
  изображение или пустая страница. Исходные файлы не изменяются никогда.
- **Операции** (`engine/document/pageOperations.ts`) — чистые функции над списком страниц.
- **История:** `documentsStore.commitPages` кладёт прежний список в `history.past`. Документ считается
  изменённым, когда текущий список — не тот же массив, что был сохранён.
- **Ресурсы** (байты PDF, разобранные документы, изображения) живут в реестре `pageRenderer`
  и освобождаются при закрытии документа.
- **Экспорт:** `engine/export/buildPdf.ts` копирует страницы объектами через pdf-lib, добавляет пустые
  и страницы-изображения, перечитывает результат. В приложении выполняется в Web Worker.
- **Запись:** main принимает байты только для путей из диалога сохранения, открытых файлов или
  выбранной папки; пишет во временный файл и атомарно заменяет целевой.

## Редактирование объектов (реализовано в фазе 4)

- **Модель** (`shared/types/objects.ts`): `EditorObject` — текст, изображение, фигура, путь. Геометрия в
  пространстве страницы: пункты, начало в левом верхнем углу видимого бокса до поворота страницы, ось y вниз.
  `document.objects[pageId]` — массив в порядке наложения.
- **Геометрия** (`engine/objects/geometry.ts`, `arrange.ts`) — чистые функции: изменение размера с
  неподвижным противоположным маркером, поворот, рамки, порядок, выравнивание.
- **Текст** (`engine/objects/textLayout.ts`): перенос и положение строк считаются один раз; результат
  рисует и SVG на экране, и экспорт. Измеритель ширины подключается отдельно (canvas с теми же шрифтами).
- **Холст** (`features/pdf-editor/PageOverlay.tsx`): SVG с `viewBox` в пунктах поверх каждой видимой
  страницы. Жесты ведут черновое состояние, в документ попадает один коммит на жест.
- **Действия** (`objectActions.ts`) идут через `documentsStore.commit`; ключ объединения сливает серии
  правок в один шаг истории.
- **Экспорт** (`engine/export/drawObjects.ts`): для каждого объекта — матрица «локальные координаты →
  PDF», затем операторы путей, `drawText` встроенным подмножеством шрифта или `drawImage`.
  Исходное содержимое страницы заключается в `q … Q`.
- **Правка существующего текста**: `PdfSource.getTextRuns` даёт строки страницы, `sampleColors` —
  цвет фона и текста по отрисованной странице, `TextRunsLayer` создаёт замещающий объект.

## Слои (реализовано в фазе 5)

- **Модель** (`shared/types/layers.ts`): `document.layers[pageId]` — стек снизу вверх; у объекта есть
  `layerId`, необязательные `groupId` и `locked`. Исходное содержимое страницы всегда лежит под стеком.
- **Операции** (`engine/layers/layerOperations.ts`) — чистые функции. `resolveObjects` выдаёт объекты
  в порядке отрисовки, без скрытых слоёв, с учтённой непрозрачностью слоя и признаком интерактивности;
  её используют холст, миниатюры и экспорт.
- **Размещение:** `objectActions.placeObjects` выбирает слой нового объекта (активный → слой типа →
  новый слой типа) в том же коммите, что и добавление объекта.
- **Экспорт:** каждый слой с объектами — OCG; содержимое слоя заключается в `/OC … BDC … EMC`, а
  видимость и блокировка записываются в `OCProperties` каталога.

## Поиск, закладки, штампы (фаза 6, часть 1)

- **Поиск:** `PdfSource.getTextRuns` даёт строки страницы с положением и углом; `engine/search/search.ts`
  (чистые функции) ищет в них и в текстовых объектах; `searchActions.runSearch` обходит страницы
  асинхронно и отменяется новым запросом. Результаты лежат в `searchStore`, подсветку рисует холст страницы.
- **Закладки:** дерево `document.bookmarks` со ссылками на идентификаторы страниц (поэтому переживают
  перестановку страниц); входят в историю. `engine/export/outline.ts` пишет `/Outlines`.
- **Водяные знаки и колонтитулы** (`features/stamps`) — не отдельная сущность, а обычные текстовые
  объекты на именованном слое, созданные одним коммитом; поэтому редактируются, скрываются и
  экспортируются теми же механизмами, что и всё остальное.

## Аннотации, ссылки, вложения (фаза 6, часть 2)

- **Заметки и ссылки — типы объектов** (`note`, `link`), поэтому слои, выделение, история и буфер
  работают для них без отдельного кода. В PDF они пишутся не графикой, а аннотациями
  (`engine/export/annotations.ts`), после сборки всех страниц — ссылке нужна ссылка на целевую страницу.
- **Круговой путь:** при открытии `PdfSource.getAnnotations` + `importAnnotations` превращают
  заметки и безопасные ссылки в объекты и запоминают номера исходных объектов PDF. При сохранении
  эти аннотации удаляются из копируемой страницы (`stripAnnotations`) и записываются заново из модели.
  Всё, что не было импортировано, копируется со страницей без изменений.
- **Внешние адреса** проходят `shared/utils/externalUrl.ts` трижды: при вводе, при записи в файл и
  в main-процессе перед `shell.openExternal`.
- **Вложения** — список в модели, байты в реестре ресурсов; запись через `PDFDocument.attach`.

## OCR, замена, изображения (фаза 6, часть 3)

- **OCR:** `engine/ocr/tesseractEngine.ts` запускает Tesseract в воркере с `workerPath`, `corePath` и
  `langPath`, указывающими в бандл (`public/tesseract`). `features/ocr/ocrActions.ts` растеризует
  страницу в отображаемом виде, передаёт PNG движку и переводит строки в пространство страницы
  (`engine/ocr/convert.ts`). Результат — `document.recognised[pageId]`, часть истории.
- **Невидимый слой:** `buildPdf.drawHiddenText` пишет строки в режиме отрисовки текста 3, подгоняя
  ширину коэффициентом сжатия глифов.
- **Замена:** `searchActions.replaceHits` правит текст объектов напрямую, а для строк страницы создаёт
  замещающие объекты (`engine/objects/replacement.ts`) одним коммитом.
- **Изображения страниц:** `features/export/imageExport.ts` экспортирует PDF, открывает его тем же
  PDF.js и растеризует; main принимает только PNG/JPEG с верной сигнатурой в выбранную папку.

## Проект, автосохранение и восстановление (реализовано в фазе 7)

- **Формат `.pdfproject`** — ZIP: `manifest.json` (формат, версия, версия приложения, время, имя),
  `document.json` (страницы, объекты, слои, закладки, вложения, распознанный текст, список источников
  с номерами перенятых аннотаций, список изображений), `sources/<id>.pdf` (исходные PDF без изменений),
  `assets/<id>` (PNG/JPEG), `attachments/<id>`. Хранится только то, на что ссылается текущее состояние.
- **Схема** — `shared/schemas/project.ts` (zod): строгие типы и пределы для каждого поля, идентификаторы
  `[A-Za-z0-9_-]{1,64}` (они же имена файлов в архиве), `PROJECT_VERSION`, цепочка `MIGRATIONS`,
  `ProjectError` с кодами `notProject`, `corruptProject`, `newerVersion`, `tooLarge`.
- **Архив** — `engine/project/projectArchive.ts`, чистый модуль без браузера и состояния:
  `writeProjectArchive` (проверяет модель той же схемой перед записью), `readProjectArchive` (пределы по
  оглавлению до распаковки, схема, миграции, целостность ссылок), `remapResourceIds` (свежие идентификаторы
  ресурсов, чтобы две открытые копии проекта не делили реестр). Используется синхронный fflate: асинхронный
  создаёт воркеры из blob-адресов, что запрещено CSP.
- **Связка с приложением** — `features/project/projectActions.ts`: `serialiseDocument` собирает байты из
  реестра ресурсов; `loadProject` пропускает каждый исходный PDF через обычный загрузчик (пароль
  запрашивается как всегда), сверяет номера страниц с реальным числом страниц, декодирует изображения и при
  ошибке освобождает всё зарегистрированное. `features/documents/documentFactory.ts` — общие кирпичи
  (загрузчик, декодер, `createDocument`), чтобы документы из PDF, изображений и проектов создавались одинаково.
- **Вид файла определяется расширением пути** (`documentFileKind`). «Сохранить» и «Сохранить как» сохраняют
  вид документа; «Сохранить как проект…» переводит документ в проект; «Экспорт в PDF…» пишет PDF-копию.
  Main проверяет соответствие содержимого расширению в обе стороны (`%PDF-` / сигнатура ZIP).
- **Автосохранение** — `features/project/autosave.ts`: по таймеру из настройки `autosaveInterval` каждый
  изменённый документ, чьё содержимое изменилось с прошлой копии, упаковывается и передаётся в main.
  Файлы пользователя автосохранение не трогает.
- **Хранилище восстановления** — `main/services/recoveryStore.ts`, папка `recovery/` в данных приложения:
  `<id>.pdfproject` + `<id>.json`, запись атомарная, данные раньше описания, операции в очереди. Хранилище
  различает копии текущего сеанса и оставшиеся от прошлого: к восстановлению предлагаются только вторые,
  при нормальном закрытии окна и выходе удаляются только первые. Каналы `recovery:list/write/read/remove`
  проверяют отправителя, идентификатор и сигнатуру данных.
- **Восстановление** — `features/project/recovery.ts` и `dialogs/RecoveryDialog.tsx`: документ открывается
  как несохранённый с прежним путём (main снова разрешает запись по этому пути), сразу получает собственную
  копию, и лишь затем удаляется старая.

## Защита паролем, поставка (реализовано в фазе 8)

- **Библиотека:** `@cantoo/pdf-lib` (MIT, форк pdf-lib) — читает зашифрованные PDF по паролю и шифрует результат.
- **Исходники:** `PdfSource.protection` (`{ password, restricted }`) заполняется при открытии: пароль — тот, что ввёл
  пользователь, `restricted` — по флагам прав из PDF.js. Пароль хранится только в реестре ресурсов в памяти.
- **Экспорт:** `ExportInput.sourcePasswords` расшифровывает исходники, `ExportInput.password` шифрует результат
  (AES-256, один пароль). Проверка результата перечитывает файл с паролем и убеждается, что без пароля он не открывается.
- **Ограничения владельца:** `hasRestrictedSource` / `assertWritable` — страницы такого файла не записываются ни в PDF,
  ни в изображения.
- **Модель:** `DocumentModel.protection` / `savedProtection` (вне истории отмены); изменение защиты делает документ
  изменённым. В проект и копии восстановления пароль не попадает.
- **Проект в воркере:** `engine/project/projectService.ts` + `project.worker.ts`; без воркеров (тесты) код выполняется на месте.
- **Открытие из ОС:** `main/services/openRequests.ts` — разбор командной строки и очередь запросов; renderer забирает
  накопленное (`documents:take-open-requests`) и подписывается на новые (`documents:open-requested`), после чего читает
  файлы обычным `openPaths` со всеми проверками.
- **Сетевой фильтр:** `main/security/requestFilter.ts` — в установленном приложении разрешены только `app:`, `blob:`,
  `data:` и служебные схемы; всё остальное отменяется на уровне сеанса, независимо от CSP.
- **Выход:** команда выхода и сигналы SIGTERM/SIGINT/SIGHUP идут одним путём: настройки дописываются на диск, копии
  восстановления текущего сеанса удаляются, затем процесс завершается.
- **Сборка:** `electron-builder.yml` — только `out/` и `package.json` в asar, иконка из `build/icon.png`
  (`npm run icon`), предохранители Electron, ассоциации файлов.

## Обновления

- `main/services/updates.ts` — `UpdateService` поверх electron-updater (в неупакованной сборке библиотека не
  загружается, состояние `unavailable`). Состояния: `idle`, `checking`, `upToDate`, `available`, `downloading`,
  `ready`, `error`. Автоматические проверки подчиняются настройке `autoUpdate` и молчат о сбоях; проверка по
  команде выполняется всегда и сообщает результат.
- `canSelfInstall` — может ли платформа установить обновление сама (сейчас всё, кроме macOS). Там, где не может,
  обновление не скачивается: пользователю показывается версия и кнопка, открывающая фиксированный адрес страницы
  выпусков (`RELEASES_PAGE_URL`); renderer этот адрес не передаёт.
- Сеть: electron-updater работает в main-процессе собственным сеансом; сетевой фильтр и CSP окна не ослаблены.
- Источник задаётся в `electron-builder.yml` (`publish`) и попадает в приложение как `app-update.yml`.
- Renderer: `features/updates/updates.ts` (состояние, однократное оповещение о каждой версии),
  `dialogs/UpdateDialog.tsx`, команда `help.checkUpdates`, флажок в параметрах.

## Шрифты

- **Встроенные** — три семейства DejaVu (`sans`, `serif`, `mono`), всегда доступны.
- **Системные** — `main/services/systemFonts.ts`: обход системных папок шрифтов, собственный разбор заголовков
  TrueType/OpenType и коллекций (.ttc) с проверкой границ; читаются только таблицы `name`, `head`, `hhea`, `OS/2`.
  Отбрасываются шрифты с запретом встраивания (`fsType`), вариативные, скрытые и слишком большие. Начертание из
  коллекции извлекается в отдельный файл. Renderer получает список семейств (`fonts:list`) и файл по имени семейства
  и начертанию (`fonts:read`) — путь он не передаёт никогда.
- **Реестр** — `renderer/engine/fonts/fontRegistry.ts`: файлы семейства загружаются при первом обращении,
  регистрируются в браузере через `FontFace` под собственным именем приложения (`PDF Editor · <семейство>`, чтобы
  браузер не подставил свой локальный шрифт) и хранятся для экспорта. `effectiveVariant` выбирает реальное
  начертание, когда запрошенного нет; этим пользуются измерение, отрисовка и экспорт, поэтому они совпадают.
- **Модель** — `TextObject.fontFamily`: идентификатор встроенного семейства или имя системного. `fontKey` даёт
  ключ, под которым байты шрифта передаются в экспорт; отсутствующее семейство заменяется встроенным и на экране, и в PDF.
- **Экспорт** — шрифт сокращается до использованных символов; если конкретный файл этого не допускает
  (проверяется на пробном документе), он встраивается целиком.

## Заметки о целевой архитектуре

- **Редактирование объектов:** вместо Konva используется собственный SVG-холст (см. раздел о фазе 4).

### Редактирование существующего текста — честные режимы

| Режим | Что происходит | Когда применяется |
| --- | --- | --- |
| Нативный | Изменение операторов текста в потоке содержимого страницы | Простые случаи: шрифт встроен полностью или заменяем, кодировка обратима (есть ToUnicode) |
| Замещение | Исходный фрагмент удаляется из потока, на его место добавляется новый текст новым шрифтом | Подмножество шрифта без нужных глифов |
| Наложение | Исходный текст закрывается подложкой, сверху новый текст. Исходный PDF-текст не меняется | Сложная вёрстка, нестандартные кодировки |
| OCR | Распознавание скана (Tesseract: eng, rus, ukr), невидимый текстовый слой | Сканы |

Интерфейс всегда будет показывать, какой режим применён. PDF.js и pdf-lib не умеют нативно
редактировать произвольный текст — потребуется собственный парсер/редактор потоков содержимого;
это главный технический риск проекта.
